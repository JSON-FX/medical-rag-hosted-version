# Implementation Report — TICKET-2: Postgres schema and the dense + lexical store adapter

**Plan**: `.claude/plans/postgres-dense-and-lexical-stores.md`

**Status**: COMPLETE

## Summary

One Postgres database now serves both retrieval legs: pgvector with an HNSW cosine index for dense, a
generated `tsvector` column with a GIN index for lexical, and both living in the same row. `PostgresDenseStore`
and `PostgresLexicalStore` implement their ports over a shared `asyncpg` pool, and the local build's query
tokeniser is ported from FTS5 syntax to `to_tsquery`.

The same 21 contract assertions now run against the fakes *and* against real Postgres. ADR-002's structural
win is collected rather than described: `LexicalStore.index()` has nothing to do, because the `tsv` column is
generated by the same insert that writes the chunk — so the local build's compensating deletes, its
exception-swallowing cleanup, and its entire `reconcile_vectors` command are not ported.

## Deviations from the plan

**1. `FakeLexicalStore` was out of contract, and the new suite caught it.** The fake tokenised queries itself
with no stopword list, so `"what is it?"` matched every chunk containing "is" while Postgres correctly
returned nothing. Both suites had been green, and the gate's `lexical_support` signal would have differed
between profiles — exactly the divergence a shared contract suite exists to prevent. Fixed by extracting
`extract_terms()` from `build_tsquery` and having both stores use it, so "what counts as a searchable term"
is shared contract rather than a Postgres detail. **This was not in the plan and is the most substantive
finding of the ticket.**

**2. `Profile` gained an explicit `resources: tuple[Lifecycle, ...]` rather than probing adapters for an
`open` attribute.** The first attempt used `getattr(adapter, "open", None)`, which would silently skip an
adapter whose method was renamed — unacceptable in a codebase that deliberately avoids `runtime_checkable`
for the same reason.

**3. Shared contract data lives in `tests/contract/stores.py`, not in `conftest.py`.** `conftest` cannot be
imported relatively (the test directories are not packages), so `CORPUS`, `StorePair`, `embedded` and
`STORE_PAIRS` moved to a sibling module that both `conftest.py` and the test files import.

**4. Postgres-specific behaviour lives in its own file.** The plan mentioned a `raw_pool` fixture for tests
needing to reach past the port; that fixture was unimplementable as specified (it read `request.param`
without being parametrised). Those tests are now `tests/contract/test_postgres_specifics.py`, which is
cleaner — they assert what the *database* enforces, which was never a port contract.

**5. Two schema additions beyond Architecture §5**, both noted in the migration and the doc:
`check (id = 1)` making `index_manifest` a true singleton, and `on delete cascade` on `chunk.document_id`.

**6. `asyncpg` and `pgvector` are an optional extra**, not base dependencies, so `dependencies = []` stays
true and `test_core_purity`'s package-level claim keeps its meaning. The dev group pulls them via
`medical-rag-hosted[postgres]`.

**7. Branched from TICKET-1's branch rather than merging PR #1.** The plan said to merge first; merging is
the human review gate, so this stacks instead. GitHub retargets the base when PR #1 lands.

**8. `db/migrate.py` and `db/README.md` were done at their planned position but the pyproject dependency
work (Task 12) was pulled forward** — `asyncpg` had to be installed before the adapter could be written.

## Issues encountered

**A `_as_vector` seam was written and removed.** It wrapped a value and returned it unchanged. Checking
`pgvector.asyncpg`'s source showed the codec already wraps a plain list, so the indirection was pure noise.

**The manual score-direction check shows 4 dense results for a 3-chunk corpus.** That is leftover data from
the integration suite's `some_drug_name_3` chunk, not a bug — the test fixtures truncate, the ad-hoc script
does not.

**Nothing about the adapter needed a second attempt.** The 21 contract assertions and the 8 integration
tests each passed on their first run against Postgres. The plan's highest-risk items — `<=>` vs `<->`, the
`init=` hook for `register_vector`, the two-argument `to_tsvector` — were all called out precisely enough
that they were avoided rather than debugged.
